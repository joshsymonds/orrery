# Engine protocol findings

This page records the stream-json protocol observed in a live recording against Claude Code 2.1.321. Each factual claim cites a fixture line as `internal/engine/capture/testdata/<file>:<line>`, with 1-based line numbers. Source claims cite the Go file and line. Fixture values are sanitised: strings outside the allow-list read `redacted`, an unlisted number reads 0 and an unlisted boolean reads false (`capture.sanitiseRun.scalar` and `capture.sanitiseRun.scalar`), and ids read like `uuid_1`.

## 1. Recording

The init line of the two-turns probe reports `claude_code_version` 2.1.321 and `model` `claude-haiku-5-5` (`internal/engine/capture/testdata/two-turns.out.ndjson:4`). The argument vector asks for the `haiku` alias (`capture.argv`), and the init line shows the resolved model name.

The recording was made by running `enginecapture record -raw DIR`, then `enginecapture sanitize -raw DIR -out DIR` (`capture.Main` and `capture.Main`). These two steps are not visible in the fixtures.

Each probe runs with a fixed argument vector (`capture.argv`). It includes `--input-format stream-json`, `--output-format stream-json`, `--include-partial-messages`, `--model haiku`, `--max-turns 2`, `--settings {"disableAllHooks":true}`, `--setting-sources ""`, `--strict-mcp-config`, `--mcp-config {"mcpServers":{}}`, and `--no-session-persistence`. The probe's permission mode and tool list are passed as `--permission-mode` and `--tools`. A probe that answers permission requests adds `--permission-prompt-tool stdio` (`capture.argv`). The child runs in a new empty directory (`capture.NewCommand`) and receives only the allow-listed environment names `HOME`, `PATH`, `USER`, `LANG`, `TERM`, `XDG_RUNTIME_DIR`, `XDG_CONFIG_HOME`, and `XDG_STATE_HOME` (`capture.envAllowed`). `HOME` is passed through as the recording machine has it, so each probe runs with the real home directory and user-level plugins, skills, agents and commands load. The init line lists entries under `agents`, `skills`, `plugins` and `slash_commands` (`internal/engine/capture/testdata/two-turns.out.ndjson:4`), but the fixture keeps one redacted entry per key (`capture.sanitiseRun.array`), so it shows neither how many entries loaded nor which of them are user-level.

The sanitiser keeps allow-listed values and replaces the rest. A string outside the allow-list becomes `redacted` (`capture.sanitiseRun.scalar`), as in `"text":"redacted"` (`internal/engine/capture/testdata/two-turns.in.ndjson:2`). A number outside the allow-list becomes 0 (`capture.sanitiseRun.scalar`), and a boolean outside it becomes false (`capture.sanitiseRun.scalar`). Each id becomes `<prefix>_<n>`, numbered from 1 for each probe (`capture.Sanitiser.sanitiseID`). One sanitiser serves every line of a probe (`capture.Sanitiser`), so the same id appears in the input and output files: `req_1` is in `internal/engine/capture/testdata/two-turns.in.ndjson:1` and `internal/engine/capture/testdata/two-turns.out.ndjson:1`. Keys of the answer object become `key_<n>` (`capture.sanitiseRun.object`), as in `key_2` at `internal/engine/capture/testdata/question.in.ndjson:3`. A line whose `type` is `rate_limit_event` is dropped (`capture.sanitiseDropped`). No fixture line carries that type.

Five further rules shape the values. An array whose elements no allow-list entry names keeps only its first element, and the rest are consumed unwritten (`capture.sanitiseRun.array`, with the named-element test at `capture.Sanitiser.namesElements`). Durations, `total_cost_usd` and the usage token counts are not on the allow-list (`capture.sanitiseAllowList`), so they read 0 (`capture.sanitiseRun.scalar`), as `"duration_api_ms":0` and `"total_cost_usd":0` do at `internal/engine/capture/testdata/two-turns.out.ndjson:13`. `num_turns` stays on the list (`capture.sanitiseAllowList`), so `"num_turns":1` at that same line is a recorded value. `credential_expires_at` is left out (`capture.sanitiseAllowList`), and the `account` object is written `{}` (`capture.sanitiseAllowList`), as at `internal/engine/capture/testdata/two-turns.out.ndjson:1`. Model and tool names are kept only from fixed lists (`capture.sanitiseKnownEntries`, checked at `capture.sanitiseRun.scalar`): the model `claude-haiku-5-5` and the tools `AskUserQuestion` and `Write`. So `"name":"AskUserQuestion"` at `internal/engine/capture/testdata/question.out.ndjson:22` is kept, and any other tool name reads `redacted`. `subagent_stats.by_type` is a data-keyed map (`capture.sanitiseAllowList`), so its keys become `key_<n>`; the fixtures write it `{}`, as at `internal/engine/capture/testdata/two-turns.out.ndjson:13`, and `modelUsage` in that line shows `key_1`.

To rerun the check, run `just engine-accept` (`justfile: engine-accept`), and pass `-keep DIR` to keep the raw output (the recipe forwards the arguments at `justfile: engine-accept`, and the flag is at `capture.cliAccept`). It runs `enginecapture accept`, which reruns the hooks-off probes live into a temporary directory and checks each probe's stdout (`capture.cliAccept` and `capture.cliAccept`). It then runs the real-settings probes with the owner's settings (`capture.cliAccept`, and the probes at `capture.SettingsProbes`). With `-keep DIR` the raw output goes into DIR, which is never removed. Accept writes no fixtures. The fixtures come from `record` and `sanitize`.

Go opens every probe with an initialize request. Its body keys are camelCase. `supportedDialogKinds` is null, `hooks` is an empty object, and `systemPrompt` is an empty array (`internal/engine/capture/testdata/two-turns.in.ndjson:1`):

```json
{"type":"control_request","request_id":"req_1","request":{"subtype":"initialize","supportedDialogKinds":null,"hooks":{},"systemPrompt":[]}}
```

The CLI answers with a success `control_response` under the same request id, before any turn line (`internal/engine/capture/testdata/two-turns.out.ndjson:1`). Its `response.response` object holds `current_permission_mode`, here `default`. The sibling keys `pending_permission_requests` and `pending_user_dialog_requests` sit one level up, at `response.`, and both are empty arrays on that line. The reply's own keys mix spellings: snake_case such as `current_permission_mode` beside camelCase such as `argumentHint` and `displayName` on the same line, so a decoder reads each field by the spelling the fixture shows.

## 3. Turns

Go writes each prompt as a user envelope with a `uuid`. The first prompt has `uuid_1` (`internal/engine/capture/testdata/two-turns.in.ndjson:2`), and the second has `uuid_15` (`internal/engine/capture/testdata/two-turns.in.ndjson:3`):

```json
{"type":"user","message":{"role":"user","content":[{"type":"text","text":"redacted"}]},"uuid":"uuid_1"}
```

The CLI echoes that uuid as `command_uuid` in three `command_lifecycle` lines, with states `queued`, `started`, and `completed` (`internal/engine/capture/testdata/two-turns.out.ndjson:2`, `:3`, `:14`):

```json
{"type":"command_lifecycle","command_uuid":"uuid_1","state":"queued","uuid":"uuid_2","session_id":"session_1"}
```

The engine session sends each prompt under its write id, a random version-4 UUID, so the envelope's `uuid` is that write id (`session.Session.Prompt`; `enginehost.newWriteID`; `transport.Transport.SendUserMessageWithUUID`, `transport.RandomUUID`). The same uuid is also listed in `user_message_uuids` on the init, status, and result lines, each set to `["uuid_1"]` (`internal/engine/capture/testdata/two-turns.out.ndjson:4`, `:5`, `:13`). The session counts a prompt as unanswered from its send until a turn's result lists its uuid in `user_message_uuids` (`session.Session.Prompt`, `session.Session.answerPrompts`; `session.turnEnded`). A turn replayed at re-adoption does not count, since its answers are to prompts the earlier holder was sent (`session.Session.answerPrompts`). A re-adopted session also counts the owed prompts: the prompts the previous controller wrote to its holder that no later stored turn end answers (see [Reconcile at start](contract.md#lifecycle-rules)). They have no uuid in the session, so a turn that lists a uuid the session did not send lowers the owed count while it is above 0 (`session.ReadoptOptions.Owed`, `session.unansweredPrompts.answer`, `session.unansweredPrompts.count`). A session re-adopted from a holder one version older is retired once the unanswered count, owed prompts included, is zero and nothing else is open (`enginehost.Manager.retireLocked`).

Each turn emits, in order, a system init line, a system status line with `status` `requesting`, the stream events for `message_start`, `content_block_start` and `content_block_delta`, an assistant line, the stream events for `content_block_stop`, `message_delta` and `message_stop`, and a result line. The first turn spans lines 4 to 13 and the second spans lines 17 to 26 (`internal/engine/capture/testdata/two-turns.out.ndjson:4-13`, `:17-26`). All of them carry session `session_1`.

The second prompt's `queued` line is at line 15, after the first turn's result at line 13 (`internal/engine/capture/testdata/two-turns.out.ndjson:13`, `:15`). The input files carry no timing, so this output order is the only evidence in the recording for when prompt two was sent.

## 11. Host notes

Control requests share the stream with events, so a host reads both from one stream. Write's `can_use_tool` arrives after `message_stop` (`internal/engine/capture/testdata/permission-allow.out.ndjson:18`, `:19`). AskUserQuestion's `can_use_tool` arrives before `content_block_stop` (`internal/engine/capture/testdata/question.out.ndjson:23`, `:24`).

The CLI chooses request ids and the host must echo them. The CLI's `req_3` at `internal/engine/capture/testdata/question.out.ndjson:23` is answered with `req_3` at `internal/engine/capture/testdata/question.in.ndjson:3`.

`orreryd --sessions` hosts each headless session as a manager, a recorder and a writer. The rules they follow are stated in [Headless sessions](contract.md#headless-sessions) of the shared contract, and this section names the code that applies them.

The manager (`internal/enginehost/manager.go`) owns the live sessions and their slots under `--session-cap`. `reserve` takes a slot before a start or resume, and the slot is freed when the session's pump ends (`enginehost.Manager.reserve`, `enginehost.Manager.pump`). `spawn` starts the process through the login shell, with `bypassPermissions` and `--permission-prompt-tool stdio` (`enginehost.Manager.spawn`, `enginehost.permissionMode`, `session.Command`). Each live session has one pump goroutine. The pump is the only reader of the session's events and the only user of its recorder (`enginehost.Manager.pump`). For each event it first calls `noteEvent`, which tracks the running turn, the open requests, the background tasks and the exit (`enginehost.Manager.recordLine`, `enginehost.Manager.noteEvent`). A pump that records an event queues its ops in order through the writer, and then sends any notice the event calls for (`enginehost.Manager.recordLine`).

The recorder (`internal/enginehost/record.go`) turns each event into store ops. It holds the unfinished text of each streaming block in memory, and each delta writes that text to the `engine_text` table (`enginehost.recorder.ops`, `enginehost.recorder.delta`). A finished block writes `engine_block`, and in the same batch removes its unfinished row (`enginehost.recorder.block`). A request that the session did not refuse writes `engine_request` and the `waiting` state with its question (`enginehost.recorder.request`, `enginehost.requestQuestion`). A turn end writes `engine_turn_ended` and the `done` state (`enginehost.recorder.ops`). An exit writes `stopped` for a clean exit, and `failed` with the reason otherwise (`enginehost.exitChanges`, `enginehost.exitFailure`).

The writer (`internal/enginehost/writer.go`) is the one goroutine that stores engine ops. Each tick, which is 100 ms by default, it sends every queued op of every session to `ApplyEngine` in one transaction (`enginehost.defaultTick`, `enginehost.Writer.Run`, `enginehost.Writer.flush`). A transaction that fails on an `EngineSet` for a session whose row is gone drops that op with a warning, fails its `Commit`, and sends the rest of the batch again within the same tick (`enginehost.Writer.flush`). Any other failure keeps all of its ops queued, in order, for the next tick (`enginehost.Writer.flush`). A session may have 256 queued non-text ops that are not yet stored, and a `Put` beyond that waits (`enginehost.defaultLimit`, `enginehost.Writer.waitForRoom`). Text ops for one block replace the queued text op of that block (`enginehost.Writer.coalesceLocked`). `Commit` returns once its ops are stored (`enginehost.Writer.Commit`).

A pump's notices are posted once their event's ops are queued; the notices of `Commit` writes (interrupted, reconcile, a failed start or resume) are posted after the write is stored. `Notify` posts the desk notice and hands the Web Push to the notice record before it returns (`internal/enginehost/notify.go`). Web Push uses `boundedPayload`, which adds the `session` key when the notice names a session (`push.boundedPayload`).

The rules, as the code applies them, are these. Each has a file and line where it is decided:

- Start records the row `working` before it spawns the process, and records `failed` when the spawn or the first prompt fails (`enginehost.Manager.start`).
- A Say to a session that is not live resumes it from its row, with the row's Claude session when it has one (`enginehost.Manager.say`, `enginehost.Manager.resume`).
- Keyed Say retry: a `Say` with a `prompt_id` whose send fails stores an `engine_prompt_failed` row in the same write as the `failed` state (`enginehost.Manager.send`, `store.EngineSet.applyEngine`). A `Say` with that `prompt_id` reads the row before it checks for a sent prompt, so it returns the failure and sends nothing, also after a restart (`enginehost.Manager.Say`, `store.Store.EnginePromptSent`). The insert keeps the first reason (`internal/store/queries.sql: InsertEnginePromptFailed`). Any other keyed failure after the prompt is stored keeps its error only while `orreryd` runs (`enginehost.Manager.execute`).
- Idle stop: `checkIdle` stops each session that has not been busy for `defaultIdleAfter`, 10 minutes, and is run every `idleCheckEvery`, 30 seconds (`enginehost.Manager.RunIdle`, `enginehost.idleCheckEvery`, `enginehost.defaultIdleAfter`). The stop records nothing, because the pump does not record an exit of a session it stops for idleness (`enginehost.Manager.noteEvent`).
- Stop: the stop signal is `SIGINT` to the process group, and `SIGKILL` after 2 seconds (`proc.defaultStopTimeout`, `proc.Process.stop`). `Stop` then records `stopped` unless the exit already recorded a state (`enginehost.Manager.Stop`, `enginehost.Manager.recordStopped`).
- Failed on death: an exit with an error is recorded `failed`, with the errors and the last stderr line as the reason (`enginehost.exitFailure`, `enginehost.exitChanges`).
- Shutdown: `Close` stops each live session, records each running turn `interrupted` with the reason `orreryd stopped during the turn`, and waits for the pumps (`enginehost.Manager.Close`, `enginehost.Manager.recordStopped`). `sessionHost.shutdown` calls it (`cmd/orreryd.sessionHost.shutdown`), and `sessionHost.stop` calls `shutdown` after the session socket has stopped (`cmd/orreryd.sessionHost.stop`), which `serve` calls at `cmd/orreryd.shutdownServe`.
- Reconcile at start: `Reconcile` clears the unfinished text of each row with no pump in this manager, and records each `working` or `waiting` row `interrupted` with the reason `orreryd restarted during the turn` (`enginehost.restartedReason`, `enginehost.Manager.Reconcile`). A session whose pump in this manager still runs, live or retired, is left to that pump, with its row and its holder (`enginehost.Manager.Reconcile`, `enginehost.Manager.pendingRows`, `enginehost.Manager.reconcileHolders`). A `working` engine row whose session has a Claude id, and whose last prompt is not `Resume working.`, is then resumed instead: `Say` sends it `Resume working.`, and its owner gets one notice, `orreryd restarted during the turn; resumed it`, in place of the interruption's. The row is `working` again and keeps the reason (`enginehost.resumePrompt`, `enginehost.resumedBody`, `enginehost.Manager.resumeOrNotify`, `enginehost.Manager.resumable`, `enginehost.Manager.resumeInterrupted`). A `waiting` row, a row with no Claude id, a row whose last prompt is already `Resume working.`, and a resume that the session cap refuses stay `interrupted`, with the reason and notice above. A resume whose spawn or send fails is recorded `failed` with its own notice. `orreryd` calls it before the session socket serves (`cmd/orreryd.startSessions`, `cmd/orreryd.sessionHost.reconcile`).
- Notices: `notifies` allows `waiting`, `done`, `failed` and `interrupted` only (`enginehost.notifies`). A turn that was interrupted sends no notice at its end (`enginehost.eventNotice`).
- Retention: `SyncServer` reads the live engine session ids once per run, from the function that `orreryd` sets to the manager's `Live` (`store.Store.SyncServer`, `cmd/orreryd.startSessions`). It then runs `pruneRetention`, which deletes the engine rows with no event at or after the 14-day cutoff, and their unfinished text and `engine_prompt_failed` rows, except the live sessions (`store.pruneRetention`). The tidy calls `SyncServer` only after its `list-panes` succeeds (`daemon.Mirror.Tidy`). All three delete statements exclude the live ids, so a session that is not live and has no event for 14 days loses its row (`internal/store/queries.sql: DeleteStaleEngineText`, `internal/store/queries.sql: DeleteStaleEnginePromptFailures`, `internal/store/queries.sql: DeleteStaleEngineSessions`).
- Errors on the session socket: `commandError` maps each error to its Connect code (`enginehost.commandError`).

### How the probes start

`enginecapture accept` runs the hooks-off probes, then five real-settings probes with the owner's settings: the guard, the resume pair (resume-plant and resume-ask, counted as one), interrupt-prompt, bypass-tool and background (`capture.SettingsProbes`, SettingsProbes). All of them run in `bypassPermissions`.

Each one starts through the owner's login shell from a bare environment (`capture.DaemonCommand`, DaemonCommand). The argument vector is `<shell> -l -c 'exec "$@"' orrery-probe <claude> <claude args>` (`capture.DaemonCommand`). The environment holds only PATH (the tmux and claude package directories, as the orreryd unit has them), HOME, USER, LANG, XDG_RUNTIME_DIR, and ORRERY_SUMMARIZER=1 (`capture.DaemonCommand`), which keeps orrery's own hook silent. The claude arguments drop `--settings` and `--setting-sources`, so the owner's settings, hooks and plugins load. MCP servers stay off (`--strict-mcp-config` with an empty config).

If the guard misses in the login form, accept retries it once without `-l` and continues in the form the guard passed in. If neither form refuses, it stops (`capture.cliSettingsSet.runProbes`, runProbes). In the recorded run the login form refused, so the fallback did not run.

`accept -keep DIR` keeps the raw output in DIR (`capture.cliAccept`), and the recipe forwards arguments (`justfile: engine-accept`). Raw output of live runs is kept outside the repository.

### Did the guard run, and what does a refusal look like

Yes, in the login form. The tool call never ran. The stream shows the refusal as the tool's result:

```json
{"type":"user","message":{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_example1","is_error":true,"content":"PreToolUse:Bash hook error: `git stash drop/clear` is blocked by the destructive-command guard: it is irreversible and has no git or checkpoint to undo it. If the user explicitly wants this, ..."}]}}
```

The model then replies in text, and the result line has `subtype` success, `is_error` false, and one `permission_denials` entry: `{"tool_name":"Bash","tool_use_id":"toolu_example1","tool_input":{"command":"<the command>","description":"<text>"}}`. No `can_use_tool` request reaches the host for it. The probe passes only on the guard's own reason text (`capture.GuardRefusal`, GuardRefusal), never on git's error.

### Do hook events appear in the stream

Yes, but only with `--include-hook-events`, which the guard probe alone passes. Each hook run is a pair of system lines:

```json
{"type":"system","subtype":"hook_started","hook_id":"hook_example1","hook_name":"PreToolUse:Bash","hook_event":"PreToolUse","session_id":"session_example","uuid":"uuid_example1"}
{"type":"system","subtype":"hook_response","hook_id":"hook_example1","hook_name":"PreToolUse:Bash","hook_event":"PreToolUse","exit_code":0,"outcome":"success","output":"...","stdout":"...","stderr":"","session_id":"session_example","uuid":"uuid_example2"}
```

Hook pairs appear for `UserPromptSubmit` (before the init line), for `PreToolUse:Bash` (three hooks start together for one Bash call; their responses can arrive after `message_stop`), and for `Stop` (two hooks, after the last `message_stop` and before the result). The guard's refusal is visible there too: its `hook_response` has `exit_code` 0, `outcome` success, and an `output` holding the guard's JSON `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"..."}}`. A refusal is a successful hook run whose output denies. It is not a hook failure, although the `tool_result` text begins `PreToolUse:Bash hook error:`; the guard's own label in that text (`` `git stash drop/clear` ``) names its rule, not the command it saw.

Without the flag, the other probes show no hook lines at all, with one exception: the resumed process printed a `hook_started`/`hook_response` pair for `SessionStart:resume` as its first two lines, before the initialize response.

### Does resume work, and does the id change

Yes. A second process started with `--resume <id>` in the first process's directory (persistence on) answered with the word the first one planted. Its init line carried the same `session_id` as the first process, so the id does not change.

Defect found and fixed on the way: the runner used to number prompt uuids from `...0001` in every process. A resumed session that already holds a prompt uuid treats a new prompt with that uuid as done. It printed only `{"type":"command_lifecycle","command_uuid":"<the reused uuid>","state":"completed",...}`, with no queued or started state, no init and no turn, and the process waited. A host must never reuse a uuid within a session. The runner now numbers a resuming probe's uuids from a separate range (`capture.runResumeUUIDFormat`).

### What follows an interrupt

The process lives and answers. The interrupt receipt is a `control_response` with success and `{"still_queued":[]}`. A `user` line carries the text `[Request interrupted by user]`. The result is `error_during_execution`, with `is_error` true and `terminal_reason` `aborted_streaming`, and the command_lifecycle state is `cancelled`. The next prompt then goes `queued`, `started`, a new init line, the turn, and a result `success`.

### Does an ordinary tool ask under bypass

No. With `--permission-mode bypassPermissions` and `--permission-prompt-tool stdio`, Bash running `git --version` sent no `can_use_tool` request. The tool simply ran (`tool_result` with `is_error` false), and the result was `success` with empty `permission_denials`. Together with section 7 of this page, under bypass only AskUserQuestion reached the host.

### What marks a live background task

Prompted to start `sleep 20` with `run_in_background: true`:

- The tool_use input carries `"run_in_background":true`.
- `{"type":"system","subtype":"background_tasks_changed","tasks":[{"task_id":"task_example","run_id":"run_example","task_type":"local_bash","description":"<text>"}],...}` arrives, then `{"type":"system","subtype":"task_started","task_id":"task_example","run_id":"run_example","task_type":"local_bash","description":"<text>","is_backgrounded":true,"tool_use_id":"toolu_example2",...}`.
- The tool_result text says the command is running in the background, with its id and an output file under claude's own temp directory.
- The turn ends normally: result `success`, `result_index` 0, `queued_turn_count` 0. Nothing in the result names the live task, and command_lifecycle is `completed`.
- While the task lives (stdin kept open), no lines arrive.
- When it ends, `task_updated` arrives with `"patch":{"status":"completed","end_time":<ms>}`, then `task_notification` with `task_id`, `run_id`, `tool_use_id`, `status` completed, `summary`, and `output_file`, then `background_tasks_changed` with `"tasks":[]`.
- Claude then starts a turn by itself: a new init line, a status line `requesting` with no `user_message_uuids`, the stream, and a result `success` with `result_index` 1 and `"origin":{"kind":"task-notification","producer":"session-task","runId":"run_example"}`. No command_lifecycle lines belong to that turn.

So the live-task marker is the non-empty `tasks` list in `background_tasks_changed` (with `task_started`). The empty list marks the end.

## 13. Forced returns

The findings of this section come from live probes on Claude Code 2.1.321 with `claude-haiku-5-5`. The probe output is not committed, so these findings cite the code that relies on each one, not fixture lines. A step's structured return depends on them (see [Step lifecycle](contract.md#step-lifecycle) of the shared contract).

- **Structured output.** A `result` carries `structured_output` when the session runs with `--json-schema` and `StructuredOutput` is among its tools. The step engine passes `--json-schema` (`session.Command`). It reads a result's `structured_output` into the turn's end, which is nil when the field is absent or `null` (`session.translator.variantEvents`, `session.structuredOutput`).
- **Repeated forcing.** A second user message after a forced return gets another forced return. `--resume` with the same flags is forced too. The step loop sends its second message through `Continue` (`enginehost.stepRun.retry`), and a respawn resumes with the step's agent and schema flags (`enginehost.Manager.respawnStep`, `session.Command`).
- **Agent settings.** `--agent` applies the agent's model, tools and body. The effort is not visible in the init line, so this section cannot confirm the effort an agent runs at. The step engine adds `--agent` with `--strict-mcp-config` (`session.Command`) and passes no `--model`, so the model comes from the agent.
- **The `StructuredOutput` tool.** An agent whose `tools:` allowlist omits `StructuredOutput` gets no `StructuredOutput` tool. Its turns then return text, with `structured_output` null. `--allowedTools` does not restore the tool, so such an agent must list `StructuredOutput` in `tools:`. An agent that uses `disallowedTools` keeps the tool.

What the step engine does with a null return: the value is nil, and the schema check fails it with `$: missing return value` (`enginehost.stepRun.turnEnded`, `enginehost.stepRun.judge`, `enginehost.validateReturn`). The return is sent back like any other failed check, and a step whose agent never forces a return ends `checks_failed` after its three send-backs.

A return is taken from a turn that ends with no background task live, and from a turn that ends while one is live only when its structured return has the step's `done_value` as its `status`. The manager tracks the live background tasks of a session and hands a turn's end over when none is live or when the turn's return is done. Any other turn end under a live task waits, so a not-done return is not read while a task stays listed (`enginehost.Manager.noteEvent`; `enginehost.stepRun.Done`; `enginehost.StepObserver.Done`). The markers of a live task are in [What marks a live background task](#what-marks-a-live-background-task).

## 14. Step and epic tools

`orrery [--socket PATH] mcp` serves the step, epic and evidence tools as an MCP server on stdin and stdout. It serves until stdin closes and exits 0, or exits 1 when the session ends on an error, such as an oversized message (see [Protocol](#protocol)). Arguments after `mcp` exit 2. The transport is stdio only, so the process opens no listener and holds no database. It is a client of the `orrery.engine.v1.Steps` service (`proto/orrery/engine/v1/step.proto: Steps`), of the `orrery.engine.v1.Epics` service (`proto/orrery/engine/v1/epic.proto: Epics`) and of the `orrery.engine.v1.Evidence` service (`proto/orrery/engine/v1/epic.proto: Evidence`) on `sessions.sock`, the socket beside the daemon socket (`protocol.SessionSocketPath`; `cmd/orreryd.startSessions`). Each step tool call makes one `Steps` RPC: `step_start` calls `StartStep`, `step_status` calls `StepStatus`, `step_stop` calls `StopStep`, `step_resume` calls `ResumeStep` and `step_wait` calls `WaitSteps` (`stepmcp.stepTools`; the handlers call them at `stepmcp.startHandler`, `stepmcp.statusHandler`, `stepmcp.stopHandler`, `stepmcp.resumeHandler` and `stepmcp.WaitSteps`). There are ten epic tools, and each call makes one `Epics` RPC: `epic_create` calls `CreateEpic`, `epic_get` calls `GetEpic`, `epic_list` calls `ListEpics`, `epic_answer` calls `AnswerEpic`, `epic_follow` calls `FollowEpics`, `epic_pause` calls `PauseEpic`, `epic_resume` calls `ResumeEpic`, `epic_stop` calls `StopEpic`, `epic_retry` calls `RetryEpic` and `epic_release` calls `ReleaseEpic`. The tool list is `stepmcp.epicTools`, and the RPC of each handler is at `stepmcp.epicCreateHandler`, `stepmcp.epicGetHandler`, `stepmcp.epicListHandler`, `stepmcp.epicAnswerHandler`, `stepmcp.epicFollowHandler`, `stepmcp.epicPauseHandler`, `stepmcp.epicResumeHandler`, `stepmcp.epicStopHandler`, `stepmcp.epicRetryHandler` and `stepmcp.epicReleaseHandler`, in that order. Each evidence tool call makes one `Evidence` RPC: `evidence_run` calls `RunEvidence`, `evidence_list` calls `ListEvidence` and `evidence_get` calls `GetEvidenceArtifact` (`stepmcp.evidenceTools`; the RPCs are at `stepmcp.evidenceRunHandler`, `stepmcp.evidenceListHandler` and `stepmcp.evidenceGetHandler`). `orrery mcp` builds the three clients and passes them to `stepmcp.NewServer`, which takes the steps, epics and evidence clients in that order (`cmd/orrery.runMCP`; `stepmcp.NewServer`, `stepmcp.newServer`).

`orrery step status ID` and `orrery step wait [--all] ID...` make the calls of `step_status` and `step_wait` on the same session socket, so a background command can watch steps without holding a tool call open (`cmd/orrery.dispatch`, `cmd/orrery.runStepWith`). `status` makes one `StepStatus` call, as `step_status` does, and prints the step object that `step_status` returns, one line of JSON (`cmd/orrery.statusStep`; `stepmcp.StepObject`). `wait` makes `WaitSteps` calls, each asking for `stepmcp.MaxWait` seconds (`cmd/orrery.waitForSteps`; `stepmcp.WaitSteps`). Unlike `step_wait`, it does not return on a timeout: an answer that names no ended step is asked again, so the command returns only when a named step has ended, and prints that step (`cmd/orrery.waitForSteps`). With `--all` it returns once every named step has ended, printing each as it ends, and each call names only the steps still running, so an ended step is not named again (`cmd/orrery.waitForSteps`). A call answered `Unavailable` is retried as the tool's is: `status` for up to 60 seconds, and `wait` until the call's own deadline (`cmd/orrery.statusStep`, `stepmcp.WaitSteps`). A refusal exits 1 with `orrery step: ` and the Connect text on stderr, which names an unknown id (`cmd/orrery.refuseStep`; `enginehost.stepCommandError`). The forms and their exit statuses, `step resume ID` included, are in [orrery](contract.md#orrery).

`orrery epic` runs the same handlers. Its forms `create`, `get`, `list`, `follow`, `answer`, `pause`, `resume`, `stop`, `retry`, `release` and `close` each make one call to the epic tool `epic_<verb>` through `CallEpicTool`, on the same session socket (`cmd/orrery.dispatch`, `cmd/orrery.runEpic`; `cmd/orrery.epicCommand`, `cmd/orrery.epicCall`; `stepmcp.CallEpicTool`). So a command and its tool make the same call. The forms are `create FILE|-`, `get ID`, `list`, `follow`, `answer EPIC --id ID [--question QN] [--choice C] [TEXT]`, `pause ID`, `resume ID`, `stop ID`, `retry ID [NODE]`, `release ID [--undo-none N]...` and `close ID --as superseded|shipped|abandoned [--by EPIC]` (`cmd/orrery.epicForms`, `cmd/orrery.epicAnswerForm`, `cmd/orrery.epicCloseForm`). `follow` takes no argument, and one with an argument is a usage error (`cmd/orrery.epicCommand`, `cmd/orrery.epicForm`). `retry` turns `NODE`, when it is given, into the tool's `node`, and an empty `NODE` is a usage error, since sending it would end the epic's park (`cmd/orrery.epicRetry`). `release` turns each `--undo-none N` into one entry of the tool's `undoNone`, in the order given. A missing `ID`, an `ID` that begins with `-`, or an `N` that is not a positive integer is a usage error (`cmd/orrery.epicRelease`). `close` turns `--as` into the tool's `kind` and `--by` into its `by`, and it is a usage error when `--as` is not `superseded`, `shipped` or `abandoned`, or when `--as superseded` has no `--by`. Such a form calls nothing (`cmd/orrery.epicClose`, `cmd/orrery.epicCloseKind`). `create` reads the tool's JSON arguments from FILE, or from stdin when FILE is `-`, and passes them as given (`cmd/orrery.epicCreate`, `cmd/orrery.epicReadInput`). `answer` turns EPIC, `--id`, `--question`, `--choice` and TEXT into the tool's `epicId`, `id`, `question`, `choice` and `text`. It leaves `question` and `choice` out when their flags are not given, and sends `text` as the empty string when TEXT is left out (`cmd/orrery.epicAnswerArgs`, `cmd/orrery.epicAnswer`). A wrong form is a usage error naming the form it wants (`cmd/orrery.epicForm`). The command prints the tool's result text on stdout, and `answer` also prints a non-empty warning on stderr (`cmd/orrery.epicAnswer`). A refusal exits 1 with `orrery: ` and the tool's text on stderr (`cmd/orrery.epicCall`; `cmd/orrery.report`). A handler error reaches the command with the prefix `epic: run TOOL: `, so an argument that does not decode reads differently there than in the tool's text (`cmd/orrery.epicCall`; `stepmcp.CallEpicTool`).

The Epics client that `orrery mcp` and `orrery epic` use sends the caller headers of the session they run in. The epic tools of `orrery mcp` and the forms of `orrery epic` use that client, and the step and evidence clients send none (`cmd/orrery.runMCP`, `cmd/orrery.runEpic`). A session that orrery started, which carries `ORRERY_SESSION`, sends `Orrery-Session` with that value. Otherwise a session in tmux sends `Orrery-Tmux` and `Orrery-Tmux-Pane` with its `TMUX` and `TMUX_PANE`, when both are set. Any other call carries no caller header (`stepmcp.CallerInterceptor`, `stepmcp.stampCaller`; `protocol.HeaderSession`, `protocol.HeaderTmux`, `protocol.HeaderTmuxPane`). `orreryd` reads these headers to record the session of each epic call (see [Epics](contract.md#epics)).

Of the Epics RPCs, `SeeEpic` alone has no tool or form: none of the eleven epic tools and none of the `orrery epic` forms makes it (`stepmcp.epicTools`; `cmd/orrery.epicForms`). The seen mark it stores is written by `serve`'s `Epics.Seen`, which the web page and the phone call (see [Epics](contract.md#epics)).

The package imports the connect client, the generated `Steps`, `Epics` and `Evidence` stubs and protobuf's JSON encoding, and its server imports the go-sdk MCP packages. It imports no database or listener package (`internal/stepmcp/tools.go: import`; `internal/stepmcp/epictools.go: import`; `internal/stepmcp/server.go: import`). The step rows live in the daemon, so a result a caller lost in transit is still in its row (`proto/orrery/engine/v1/step.proto: Steps.StepStatus`, `proto/orrery/engine/v1/step.proto: Step.result`).

### Protocol

The server runs on the official MCP Go SDK, go-sdk v1.8.0 (`go.mod: require github.com/modelcontextprotocol/go-sdk`). Citations to `go-sdk v1.8.0` name its files, and the others name this repository.

- Messages are newline-delimited JSON-RPC 2.0 (`go-sdk v1.8.0 mcp.IOTransport`; `stepmcp.Server.Serve`). The server reports the `tools` capability alone, with `listChanged` omitted, and the server name `orrery` with version `1` (`stepmcp.Server.sdk`; `go-sdk v1.8.0 mcp.Server.capabilities`; `TestInitializeNamesTheServerAndAdvertisesOnlyTools`).
- **Revision.** In an `initialize` request, the server answers the revision the client requests when it is `2025-11-25`, `2025-06-18`, `2025-03-26` or `2024-11-05`. Any other revision, `2026-07-28` included, gets `2025-11-25`, and the server does not refuse the `initialize` request for it (`go-sdk v1.8.0 mcp.supportedProtocolVersions`, `go-sdk v1.8.0 mcp.negotiatedVersion`; `go-sdk v1.8.0 mcp.NewServer`, `go-sdk v1.8.0 mcp.ServerSession.initialize`; `TestInitializeNamesTheServerAndAdvertisesOnlyTools`).
- **Per-request revision.** go-sdk v1.8.0 also serves the sessionless protocol of revision `2026-07-28`, which orrery does not turn off. A call whose params `_meta` carries `io.modelcontextprotocol/protocolVersion` of `2026-07-28` or later and a valid `io.modelcontextprotocol/clientCapabilities` takes the per-request path and is served without `initialize`; such a call with missing or invalid capabilities is refused with `-32602`; the server takes that call's revision and capabilities as the session's when none is set. On that path `initialize` and `ping` are refused with `-32601` and the text `"<method>" is not supported in the new protocol`, and a revision the server does not support is refused with the SDK's unsupported-version error (`go-sdk v1.8.0 mcp.validateRequestMeta`; `go-sdk v1.8.0 mcp.MetaKeyProtocolVersion`, `go-sdk v1.8.0 mcp.MetaKeyClientCapabilities`; `go-sdk v1.8.0 mcp.ServerSession.handle`).
- **Ping.** Off the per-request path, `ping` gets an empty result, `{}`, before and after `initialize` (`go-sdk v1.8.0 mcp.serverMethodInfos`, `go-sdk v1.8.0 mcp.ServerSession.handle`, `go-sdk v1.8.0 mcp.ServerSession.ping`; `TestPingGetsAnEmptyResultBeforeAndAfterInitialize`).
- **Before initialize.** Off the per-request path, a `tools/list` or `tools/call` sent before the `initialize` request is refused with JSON-RPC error code `0` and the text `method "tools/list" is invalid during session initialization`, naming the method. The gate opens at the `initialize` request, not at `notifications/initialized` (`go-sdk v1.8.0 mcp.ServerSession.handle`; `go-sdk v1.8.0 jsonrpc2.toWireError`).
- **Cancellation.** A `notifications/cancelled` gets no reply. It cancels the request it names, and its effect depends on the tool that request calls (`go-sdk v1.8.0 mcp.canceller.Preempt`; `go-sdk v1.8.0 jsonrpc2.Connection.Cancel`; `go-sdk v1.8.0 mcp.serverMethodInfos`).
  - `step_status`, `step_wait`, `epic_get`, `epic_list`, `epic_follow`, `evidence_list` and `evidence_get` are reads and waits. Their handler's context ends with the cancel, so the daemon call stops, and the call's slot frees when the handler returns (`stepmcp.limitToolCalls`, `stepmcp.callContext`; `TestCancelFreesAWaitSlotForANinthCall`).
  - The twelve mutating tools, `step_start`, `step_stop`, `step_resume`, `epic_create`, `epic_answer`, `epic_pause`, `epic_resume`, `epic_stop`, `epic_retry`, `epic_release`, `epic_close` and `evidence_run`, are detached from the cancel. Their handler's context ends only with the connection, so each finishes its one daemon call (`stepmcp.mutatingTool`, `stepmcp.callContext`; `TestCancelLeavesAMutatingCallRunning`). A detached call also ends with the connection when its input closes or its serve context is canceled (`TestConnectionEndEndsADetachedCall`).
  - The SDK still writes the answer of a cancelled call, because the response write does not observe the cancel (`go-sdk v1.8.0 jsonrpc2.Connection.processResult`, `go-sdk v1.8.0 jsonrpc2.notDone`).
- **Eight calls.** A connection runs at most 8 `tools/call` requests at once. A ninth is refused at once with `-32000` and the text `Server already has 8 tool calls in flight`. It is not queued, and its handler never starts (`stepmcp.maxToolCalls`, `stepmcp.limitToolCalls`; `TestNinthToolCallIsRefusedAtOnceAndNeverStarts`).
- **Message size.** A message longer than 1 MiB ends the session. The server reads no more than 1 MiB of it and answers nothing for it. `Serve` returns an error, so `orrery mcp` exits 1 with that error on stderr (`stepmcp.maxFrameBytes`, `stepmcp.Server.Serve`; `go-sdk v1.8.0 mcp.frameLimitReader`, `go-sdk v1.8.0 mcp.frameLimitReader.Read`, `go-sdk v1.8.0 mcp.frameLimitReader.resetFrame`; `TestOversizedInboundLineEndsTheSessionWithBoundedMemory`; `cmd/orrery.runMCP`, `cmd/orrery.report`).
- **Unknown method.** After `initialize`, or on the per-request path, a method the server does not serve is refused with `-32601` and the text `method not found: "<method>"` (`go-sdk v1.8.0 mcp.defaultReceivingMethodHandler`; `go-sdk v1.8.0 jsonrpc2.Connection.processResult`; `go-sdk v1.8.0 jsonrpc2.ErrMethodNotFound`; `go-sdk v1.8.0 jsonrpc2.toWireError`).
- **Unknown tool.** A `tools/call` for a name the server does not serve is refused with `-32602` and the text `unknown tool "<name>"` (`go-sdk v1.8.0 mcp.Server.callTool`).
- **Arguments.** A call without arguments reaches the handler as `{}`. Arguments that are not a JSON object are refused with `-32602` and the text `Tool arguments must be an object` (`stepmcp.toolHandler`; `TestToolArgumentsAbsentAreAnEmptyObjectAndNonObjectsAreRefused`).
- **Handler errors.** A handler error is not a JSON-RPC error. It is a tool result whose single text block is the error's message, with `isError` true (`stepmcp.toolHandler`). Argument errors, refused starts and daemon failures all arrive this way (`stepmcp.decodeArguments`, `stepmcp.toolFailure`).
- **Tool list.** `tools/list` lists the eighteen tools sorted by name (`go-sdk v1.8.0 mcp.featureSet.all`, `go-sdk v1.8.0 mcp.featureSet.sortKeys`; `go-sdk v1.8.0 mcp.NewServer`, `go-sdk v1.8.0 mcp.Server.listTools`; `TestToolsListMatchesTheBaseFixture`).
- **Known SDK issues.** Orrery accepts go-sdk issue #1235, in which a cancelled call is still answered, and go-sdk issue #1389, in which a request id may be reused.
- The refusals above that the SDK produces may change with the SDK. This section records them as go-sdk v1.8.0 gives them.

### Arguments and results

Every successful tool result is one text block holding JSON. Every argument object refuses unknown keys, so a misspelt key is an error (`stepmcp.decodeArguments`; `stepmcp.decodeProto`).

#### step_start

Arguments (`stepmcp.startArgs`). Required: `prompt` and `workspace` (`stepmcp.startArgs`). Optional:

- `revision`: the commit the step starts at. Empty means HEAD (`proto/orrery/engine/v1/step.proto: StartStepRequest.revision`).
- `doneValue`: the status the done return carries. Empty means `done` (`proto/orrery/engine/v1/step.proto: StartStepRequest.done_value`).
- `readOnly`: a read-only step runs in a detached worktree removed when it ends (`proto/orrery/engine/v1/step.proto: StartStepRequest.read_only`).
- `ownedPaths`: the repository-relative paths a writing step may change.
- `gateName`: the name of the gate the step's return is checked against. It is resolved once, when the step starts, from `gatesFile` and then the project file. Empty runs no gate (`stepmcp.startArgs.GateName`; `proto/orrery/engine/v1/step.proto: StartStepRequest.gate_name`; see [Gate files](contract.md#gate-files)).
- `gatesFile`: the absolute path of the epic's gates file, read before the project file. Empty reads only the project file. It is refused when it is not absolute, and when it is set without `gateName` (`stepmcp.startArgs.GatesFile`; `proto/orrery/engine/v1/step.proto: StartStepRequest.gates_file`; `enginehost.Steps.resolveStepGate`).
- `epic`: the epic the step belongs to, passed as given. Empty leaves the step unlabelled, and an unlabelled step is never listed. The format `step.proto` names, `<repo-id>/<epic-slug>`, is not checked (`stepmcp.startArgs.Epic`, `stepmcp.startHandler`; `proto/orrery/engine/v1/step.proto: StartStepRequest.epic`).
- `task`: the slug of the epic's task the step works on. Empty when it works on no one task (`stepmcp.startArgs.Task`, `stepmcp.startHandler`; `proto/orrery/engine/v1/step.proto: StartStepRequest.task`).

`gate` and `gateLimitSeconds` are not arguments. A call that names either one is refused as an unknown key (`stepmcp.decodeArguments`). The gate's limit is the one its definition gives (see [Gate files](contract.md#gate-files)).

`schema` is a JSON object argument, not a string; the server sends its JSON text to `StartStep` (`stepmcp.schemaText`, `stepmcp.startHandler`). `prompt` and `workspace` must be non-empty (`stepmcp.startHandler`). `agent` and `schema` may be left out of the call. The service refuses an empty `agent` or `schema` unless the start names an agent gate (`enginehost.checkStep`, `enginehost.Steps.resolveStart`). A start that names an agent gate by `gateName` must be `readOnly` and leave `agent`, `schema` and `doneValue` empty, since the gate supplies them (`enginehost.agentGateStart`; see [Agent gates](contract.md#agent-gates)).

Result: `{"id": "<step id>"}`, returned once the step's row exists (`stepmcp.startHandler`; `proto/orrery/engine/v1/step.proto: Steps.StartStep`). A refused start returns the refusal and no id.

#### step_status

Arguments: `id`, required and non-empty (`stepmcp.idArgs`, `stepmcp.statusHandler`). Result: the step object described below (`stepmcp.statusHandler`).

#### step_stop

Arguments: `id`, required and non-empty. Result: `{"id": "<step id>", "stopped": true}` (`stepmcp.idCallHandler`, `stepmcp.stopHandler`). The result says `stopped: true` whenever the daemon accepted the call, since `StopStepResponse` has no fields (`proto/orrery/engine/v1/step.proto: StopStepResponse`).

#### step_resume

Arguments: `id`, required and non-empty (`stepmcp.idArgs`, `stepmcp.idCallHandler`). Result: `{"id": "<step id>", "resumed": true}` (`stepmcp.idCallHandler`, `stepmcp.resumeHandler`). The result says `resumed: true` whenever the daemon accepted the call, since `ResumeStepResponse` has no fields (`proto/orrery/engine/v1/step.proto: ResumeStepResponse`). The call resumes a step that a usage limit holds, through `ResumeStep` (see [Usage-limit hold](#usage-limit-hold)); `ResumeStep` refuses a step that no limit holds with `failed_precondition`.

A refused call is a tool error whose text is the Connect error's text, such as `failed_precondition: step is not limited` (`stepmcp.idCallHandler`; `enginehost.stepCommandError`). Its codes are those of `ResumeStep` in [Steps](contract.md#steps). A call answered `Unavailable` is sent again for up to 60 seconds (`stepmcp.idCallHandler`; `rpcretry.Window`, `rpcretry.Do`). The retry does not treat `step is not limited` as a resume. After a cut attempt that resumed the step, the retry answers that refusal, where `orrery step resume` exits 0 (`stepmcp.idCallHandler`, `stepmcp.resumeHandler`; `cmd/orrery.resumeStep`).

#### step_wait

Arguments (`stepmcp.waitArgs`):

- `ids`: a non-empty array of step ids. An empty id is refused, and so is an empty list (`stepmcp.waitHandler`).
- `timeoutSeconds`: optional. It must be a whole number of seconds, 0 or more. A fractional or negative value is an error with the text `timeoutSeconds must be a whole number of seconds, 0 or more` (`stepmcp.waitSeconds`).

The wait is clamped to `MaxWait`, 25 minutes or 1500 seconds (`stepmcp.MaxWait`). An omitted timeout is 1500 seconds. A timeout at or above 1500 is 1500 (`stepmcp.waitSeconds`). The clamp exists so that the call returns inside the time Claude Code allows a tool call, and the caller asks again (`stepmcp.MaxWait`). A timeout of 0 returns at once (`proto/orrery/engine/v1/step.proto: WaitStepsRequest.timeout_seconds`).

Result: `{"ended": <step or null>, "steps": [<step>, ...]}` (`stepmcp.waitResult`, `stepmcp.waitHandler`). `ended` is the first step to end and is `null` when the timeout passes first. `steps` lists every named step in the order the request named them (`proto/orrery/engine/v1/step.proto: WaitStepsResponse`). On a timeout the caller reads each step's state from `steps`.

#### The step object

Every tool that reports a step returns these fields, and so does `orrery step status` and each step `orrery step wait` prints (`stepmcp.stepJSON`, `stepmcp.stepFromProto`, `stepmcp.StepObject`):

- `id`, `agent`, `workspace`, `revision`, `readOnly`, `worktree`: as the `Step` message defines them (`proto/orrery/engine/v1/step.proto: Step`). `worktree` is empty for a writing step.
- `end`, `reason`: empty while the step runs (`proto/orrery/engine/v1/step.proto: Step.end`, `proto/orrery/engine/v1/step.proto: Step.reason`).
- `status`: the done value the return carried, or the status the step ended with. `result`: the latest result the return carried (`proto/orrery/engine/v1/step.proto: Step`).
- `checks`: each `{round, name, ok, detail}` from the rounds the return's checks ran in, without the tails a check kept (`stepmcp.checkJSON`, `stepmcp.stepFromProto`; `proto/orrery/engine/v1/step.proto: Step.checks`).
- `started`, `ended`: unix seconds. `ended` is 0 while the step runs (`proto/orrery/engine/v1/step.proto: Step`).
- `limited`, `limitKind`, `limitResets`: whether a usage limit holds the step, the kind of that limit, and its reset in unix seconds. The kind is empty when it is unknown, and the reset is 0 when it is unknown. Both are empty or 0 when no limit holds the step (`proto/orrery/engine/v1/step.proto: Step`; `enginehost.stepMessage`).

The engine `Step` message has five fields that the step object does not carry, so `step_status` and `step_wait` do not report them: `stage` and `stage_started`, the stage the step's loop is in and the unix seconds it started; `gate_name`; `gate_limit_seconds`, the gate's limit in whole seconds; and `verdicts`, the monitor and judge verdicts as `StepVerdict` messages, each with `round`, `kind` (`monitor` or `judge`), `verdict` and `detail` (`proto/orrery/engine/v1/step.proto: Step`, `proto/orrery/engine/v1/step.proto: StepVerdict`). `stepmcp.stepJSON` names no field for them, and `stepmcp.stepFromProto` maps none. The stages, and when the loop writes each one, are in [Step lifecycle](contract.md#step-lifecycle), Stage.

Refusals: a refused call is a tool error. #### epic_answer

- `invalid_argument` with `choice: a note answers no question` for a note that names a `choice`, with `text: empty` for a note whose text is blank, and with `choice: empty` for a question that names no `choice` (`enginehost.checkEpicAnswer`).

#### epic_pause

Arguments: `id`, required (`stepmcp.epicTools`). Result: the stored epic, with `paused` true (`stepmcp.epicPauseHandler`). The write sets `paused` and records the owner as the pause source, and it closes the epic's due rows, so the planner starts no turn for the epic and no reset resumes it (`store.Store.PauseEpic`, `store.pauseAsOwner`; `internal/store/queries.sql: PauseEpic`, `internal/store/queries.sql: SetEpicPauseSource`). An epic the owner paused, or paused with no recorded source, is refused with `failed_precondition` and the text `epic <id> is already paused` (`store.Store.PauseEpic`; `enginehost.epicControlError`). An epic a usage limit paused is accepted: its pause becomes the owner's and its due row closes, so it stays paused past the reset (`store.Store.PauseEpic`).

#### epic_resume

Arguments: `id`, required (`stepmcp.epicTools`). Result: `{"epic": <StoredEpic>, "resumed": [<step id>, ...], "stillLimited": [<step id>, ...]}`, the `ResumeEpicResponse` in protobuf JSON, where each list is `[]` when it is empty (`stepmcp.epicResumeHandler`, `stepmcp.protoResult`; `proto/orrery/engine/v1/epic.proto: ResumeEpicResponse`). The `epic` is the stored epic read back, with `paused` as the call left it. `resumed` lists the limited task steps the call resumed, oldest first. `stillLimited` lists those a full step cap left limited, oldest first. The keys are protojson's lower camel case, so `still_limited` reads `stillLimited`. An empty `id` is `invalid_argument` with `id: empty`, and an unknown epic is `not_found` with `id: no epic <id>` (`enginehost.epicService.ResumeEpic`).

The call clears `paused` and its pause source, closes the epic's due rows, and resumes the epic's limited task steps: the open steps that a usage limit holds and that carry a task label. A build step carries `T<seq>`, an evidence judge step carries `evidence-<run id>`, a review or closure step carries the path of its node run, and a planner turn's step carries none, so it is not resumed (`enginehost.epicService.limitedTaskSteps`). The store's `ResumeEpic` runs when the epic is paused or holds no such step. It clears `paused`. An epic that is not paused and holds no such step is refused with `failed_precondition`: `epic <id> is parked, not paused; retry ends a park` when the epic is parked, or `epic <id> is not paused` otherwise. An epic that is not paused and holds such a step is resumed without a refusal, since the store is not called (`enginehost.epicService.ResumeEpic`; `store.Store.ResumeEpic`, `store.resumeEpic`; `internal/store/queries.sql: ResumeEpic`). A park stays, and `epic_retry` ends it.

Each limited step is resumed by `Steps.Resume`, which sends the owner's resume prompt in the step's loop (`enginehost.epicService.ResumeEpic`; `enginehost.Steps.Resume`). A resume that the step cap refuses leaves the step limited and lists it in `stillLimited`. A step that is no longer limited, or has ended, is in neither list (`enginehost.epicService.ResumeEpic`). Any other error from a step's resume is `internal` with its text. The call stops there, the steps resumed before it stay resumed, and a pause the store cleared stays cleared (`enginehost.epicService.ResumeEpic`).

#### epic_stop

Arguments: `id`, required (`stepmcp.epicTools`). Result: the stored epic, with `paused` true, or with `paused` as it was in the release case below (`stepmcp.epicStopHandler`). One write pauses the epic as the owner's, closes the epic's due rows, and flags its running turn to stop. The store returns the turn's step, which is empty while the turn has none (`store.Store.StopEpic`; `internal/store/queries.sql: SetEpicTurnStop`). The service then stops that step, as `StopStep` does (`enginehost.epicService.StopEpic`). A turn with no step is stopped when its step's id is recorded (`planner.Runner.startStep`). An epic with no running turn is refused with `failed_precondition` and the text `epic <id> has no running turn`, and nothing is stopped, unless it holds its repository's release slot (`store.Store.StopEpic`; the release case is below). A failed step stop comes after the write, so the epic stays paused and flagged, and its error is `internal` with the error's text (`enginehost.epicService.StopEpic`, `enginehost.epicStoreError`).

The release case applies to an epic with no running turn that holds its repository's release slot, and it is not refused. One write frees the slot and returns the id of the first step, in the order the store reads them, of the epic's release node runs at their current attempts that has no end, or empty when none does. The service stops that step as above. The epic is not paused, and its phase does not change. The result is the stored epic (`store.stopReleaseSlot`, `store.openReleaseStep`, `enginehost.epicService.StopEpic`; see [Release](contract.md#release)).

#### epic_retry

Arguments: `id`, required, and `node`, optional: the workflow node id whose parked runs, or else its failed latest integrate run, rerun (`stepmcp.epicRetryArgs`; `proto/orrery/engine/v1/epic.proto: RetryEpicRequest.node`). Result: the stored epic, with `parked` empty (`stepmcp.epicRetryHandler`).

Without `node`, one write ends the park, sets the epic's `retried` to its highest turn seq, so the failed turns up to that seq stop counting toward a park, and turns each parked loop of the epic running with one more granted round, so its next round runs. Its triggers stay pending, `paused` is unchanged, and each open park question is answered `retry` (`store.Store.RetryEpic`, `store.closeParkQuestions`, `store.grantParkedLoops`; `internal/store/queries.sql: RetryEpic`, `internal/store/queries.sql: GrantEpicParkedLoops`). An epic that is not parked is refused with `failed_precondition` and the text `epic <id> is not parked` (`store.Store.RetryEpic`).

With `node`, the call reruns each parked run of that node id under its next attempt, and ends the park in the same write, answering each open park question `retry` as well. A parked run's outcome, output, revision, refs, result and end are cleared, so its work is prepared and started again under the new attempt. When the node has no parked run and its latest integrate run ended `failed`, that one run alone reruns under its next attempt instead: its outcome, output, refs checked and end are cleared, and its revision and result are kept, so its Done gates walk again on the same candidate (`store.retryFailedIntegrate`; `internal/store/queries.sql: RetryFailedEpicIntegrateRun`). The epic's `retried` is set as without `node`, but no loop is granted a round, and a loop id is not a node a retry names (`store.Store.RetryNode`; `internal/store/queries.sql: RetryEpicNode`; `enginehost.epicService.retryPark`). A node with nothing to rerun is refused with `failed_precondition` and the text `node <node> of epic <id> is not parked`, and nothing is written (`enginehost.epicControlError`, `store.Store.RetryNode`). Nothing to rerun is no parked run and no latest integrate run that ended `failed`, so a running or passed latest integrate run, and an earlier failed run that a later run of the node superseded, are refused the same way. An epic in phase `met_at_base`, which the owner's `end` answer to a met-at-base park question sets, is parked for good: the call without `node`, and the call naming its parked node, are refused with `failed_precondition` and the text `epic <id> is parked for good: <park reason>`, with nothing written; a `node` with nothing to rerun gets the not-parked refusal above (`store.Store.RetryEpic`, `store.Store.RetryNode`, `enginehost.epicControlError`; see [Epics](contract.md#epics)). An epic parked by a met-at-base question that its owner has not ended is not refused: the call without `node`, and the call naming its parked evidence node, rerun that run at its next attempt and end the park, answering the question `retry`, as the answer does (`store.rerunMetAtBaseRuns`, `store.Store.RetryEpic`; see [Workflows](contract.md#workflows)). A `node` that is the epic's release node is refused with `failed_precondition` and the text `node <node> of epic <id> is the release; resume it with orrery epic release <id>`, with nothing written; `epic_release` resumes it (`store.Store.RetryNode`; see [Release](contract.md#release)).

#### epic_release

Arguments (`stepmcp.epicReleaseArgs`): `id`, required, and `undoNone`, optional: an array of the 1-based positions of the undo-none release steps to run again. Omit it to name none. Its JSON key is `undoNone` for the request's `undo_none` field (`proto/orrery/engine/v1/epic.proto: ReleaseEpicRequest`; `stepmcp.epicReleaseHandler`). Result: the stored epic, as [epic_get](#epic_get) gives it, with `releases` and `releaseSlot` (`stepmcp.epicReleaseHandler`).

The call is the `ReleaseEpic` RPC, and it releases the epic in one of two ways. A stopped release resumes at its first unfinished step, and it runs again each undo-none step that `undoNone` names. An epic that ended with gaps is released on the owner's word: the store logs that as the owner's decision, `undoNone` must be empty for it, and the epic is then clean, so its release node takes the release slot as a clean epic's does (see [Release](contract.md#release)). The service refuses an empty `id` with `invalid_argument` and `id: empty`, and a position below 1 with `invalid_argument` and `undo_none: position <n> is below 1`, before the store is asked. An unknown epic is `not_found` with `id: no epic <id>` (`enginehost.epicService.ReleaseEpic`, `enginehost.epicControlError`). A refusal of the state of the release is `failed_precondition` with the store's text, and nothing is written, such as `epic <id> is not stopped`, `position <n> of epic <id> is not an undo-none release step`, or `epic <id> has not started a release; name no undo-none step`, which an epic that ended with gaps gets when `undoNone` names a position. Each text is listed under [Release](contract.md#release) (`store.checkReleaseResume`, `store.namedUndoNone`). The refusal is a tool error whose text is the Connect error's text, as [Protocol](#protocol) describes. `orrery epic release` makes this call too (see [orrery](contract.md#orrery)).

#### epic_close

Arguments (`stepmcp.epicCloseArgs`): `id`, required; `kind`, required, one of `superseded`, `shipped` and `abandoned`; and `by`, optional: the epic that replaces the closed one. `superseded` requires `by`. The JSON keys are the request's `id`, `kind` and `by` (`proto/orrery/engine/v1/epic.proto: CloseEpicRequest`; `stepmcp.epicCloseHandler`). Result: the stored epic, as [epic_get](#epic_get) gives it, whose `phase` is `closed_superseded`, `closed_shipped` or `closed_abandoned` (`stepmcp.epicCloseHandler`).

The call is the `CloseEpic` RPC (`enginehost.epicService.CloseEpic`). The closer is the planner when the call's `Orrery-Session` header names the step of the epic's running turn, which is the session the planner's own calls run in. Any other call is the owner's, and so is a call with no session header (`enginehost.epicService.closerOf`; `protocol.HeaderSession`). One write in the store closes the epic (`store.Store.CloseEpic`):

- its `phase` becomes the closed phase of `kind`, and `closed_by` records the closer and `superseded_by` records `by`;
- its park is cleared, its pause is cleared and its due resumes close, so no reset resumes it;
- each open question is answered with the closed phase as its `choice`, so the epic has no open question;
- its running turn ends `free` with the reason `epic closed as <kind>`, so the turn does not count toward a park, and the triggers the turn claimed return to pending;
- each running node run ends with no outcome, and each pending trigger is consumed, so the planner has nothing to claim;
- a release slot the epic holds is freed (`store.Store.CloseEpic`, `store.closeEpicRows`, `store.endClosedTurn`).

A planner close also adds one tell, `Closed as <kind>.`, or `Closed as <kind> by <by>.` for superseded. That tell is the ending the owner is told, and it is the one report a close routes: the epic needs a report, and its ending is a notice that opens on the report (`store.UnreportedEpics`, `planner.reportedPhase`). An owner close adds no tell and needs no report, so it routes none (`store.closeEpicRows`, `store.UnreportedEpics`). The service then stops the turn's step, which the store returned, and each other running step of the epic, each once, as `StopEpic` stops a step (`enginehost.epicService.stopClosedSteps`). The result is the epic read back after the stops. A step that is not running is left alone.

The closed epic is not live in the epic list, and the interpreter, the builder and the planner's claim skip it: no node, build or planner turn starts on it (`server.storedEpicMessage`, `interpret.Runner.Pass`, `store.BuildEpics`, `store.checkClaimable`, `kinds.Ended`).

The service refuses an empty `id` with `invalid_argument` and `id: empty`, before the store is asked. An unknown epic is `not_found` with `id: no epic <id>`. Every other refusal is `failed_precondition` with the store's text, and nothing is written or stopped: `kind "<kind>" is not superseded, shipped or abandoned`, and `epic <id> is superseded and names no epic that replaces it` (`store.closeEndOf`, `enginehost.epicControlError`). A `by` that a close of another kind names is recorded in `superseded_by` as named, and is not refused.

#### epic_follow

Arguments: none. The schema is an object with no properties, and any key is refused (`stepmcp.epicFollowArgs`; `stepmcp.epicFollowHandler`). Result: `{"follows": [...]}`, the `FollowEpicsResponse` in protobuf JSON, with one `EpicFollow` for each question label, in label order, each with `label`, `answered` and `followed`. The counts are across all epics, as [FollowEpics](contract.md#epics) gives them. Protobuf JSON writes each count as a string, and `follows` reads `[]` when no answered question had a recommendation (`stepmcp.epicFollowHandler`, `stepmcp.protoResult`; `proto/orrery/engine/v1/epic.proto: FollowEpicsResponse`). It is a read, so a cancel ends its call (see [Protocol](#protocol)). Its refusals are `unavailable` with `epic store unavailable` when orreryd has no store, and `internal` with the store's error text when the read fails (`enginehost.epicService.FollowEpics`, `enginehost.epicService.ready`, `enginehost.epicStoreError`).

#### Evidence tools

The three evidence tools call the `orrery.engine.v1.Evidence` service on `sessions.sock` (`proto/orrery/engine/v1/epic.proto: Evidence`). Their input schemas are inferred from the argument structs `evidenceRunArgs`, `evidenceListArgs` and `evidenceGetArgs` (`stepmcp.evidenceRunArgs`, `stepmcp.evidenceListArgs`, `stepmcp.evidenceGetArgs`; `stepmcp.argumentSchema`). Every argument object refuses unknown keys, as the other tools do. A refusal is a tool error whose text is the Connect error's code and message (see [Protocol](#protocol)).

`evidence_run` runs an item's evidence. Required: `epic`, `item`, `revision` and `phase`, all strings. `item` is a Requirement's id, `R<n>`, and any other name is refused. `phase` is `red` or `green`. `revision` is any revision git resolves (`stepmcp.evidenceRunArgs`; `enginehost.Evidence.Run`). Result: the `EvidenceRun` the call stored, in state `capturing`, with no verdict yet. The run is driven in the background, and [Evidence](contract.md#evidence) gives what happens next. Its refusals are those of `RunEvidence`: `invalid_argument` with `epic: empty`, `item: empty`, `revision: empty` or `phase: empty` (`enginehost.evidenceServiceCheckRun`), and with the reason of a refused item, phase or revision (`enginehost.Evidence.Run`, `enginehost.evidenceRunItemOf`); `not_found` with `epic: no epic <id>` (`enginehost.evidenceServiceRunError`).

`evidence_list` lists an epic's runs. Required: `epic`. Result: the `ListEvidenceResponse` in protobuf JSON, `{"runs": [...]}`, with each run's artifacts. The runs come in the order the store gives them, by creation and then id (`store.Store.EvidenceRuns`). An empty `epic` is `invalid_argument` with `epic: empty` (`enginehost.evidenceService.ListEvidence`).

`evidence_get` returns one artifact of a run. Required: `run`. Optional: `name`, the artifact's repository-relative path, which is omitted for the run's stdout log. Result: the `GetEvidenceArtifactResponse` in protobuf JSON, with `data` as base64 and `hash` (`stepmcp.evidenceGetArgs`, `stepmcp.evidenceGetHandler`; `stepmcp.protoResult`; `enginehost.evidenceService.GetEvidenceArtifact`). Its refusals: `invalid_argument` with `run: empty`, `not_found` with `run: no run <id>` for an unknown run, and `not_found` with `name: no kept artifact <name>` for a name the run does not keep (`enginehost.evidenceService.GetEvidenceArtifact`).

### The planner's return

A planner turn's step returns through a forced return, as [section 13](#13-forced-returns) describes. Its schema is `Schema` in `internal/planner/plan.go`, and the step starts with it (`planner.Runner.startStep`; `planner.Schema`). The schema requires `status`, `decisions`, `tasks`, `outline`, `questions` and `outcome`, and refuses any other key at the top level. `status` must be `done`, and `outcome` must be `work`, `wait` or `complete`. Each task requires `title`, `deliverable`, `files`, `requirements`, `contributes`, `test_changes`, `gate` and `evidence`, and refuses any other key. The `evidence` object requires `capture`, `limit`, `artifacts`, `supplied`, `conclusion`, `judge`, `kind` and `tests`, and refuses any other key, so a task that still names `check` fails the schema (`planner.Schema`). Each question requires `label`, `text`, `choices`, `recommended`, `why`, `confidence` and `replaces`, and refuses any other key. Each choice requires `id` and `does`, and refuses any other key. `confidence` must be `low`, `medium` or `high` (`planner.Schema`). A return that passes the schema is then checked by the plan check, and a refusal is sent back to the session (see [Planner turns](contract.md#planner-turns)). The plan check refuses a `test_changes` path that is not one of the task's `files` (`planner.testChangeRefusals`).

### Usage-limit hold

A usage limit holds a step until the step is resumed or stopped. [Step lifecycle](contract.md#step-lifecycle) of the shared contract, under Usage limit, gives the rules. This subsection gives what the tools and the protocol show.

- A turn is limited by a rejected rate limit stored at or after its prompt, or by an assistant error `rate_limit` (`enginehost.stepRun.limitTurn`; `enginehost.stepRun.Event`; `session.assistantEvents`). A limited turn is no round, and the step is released: its process is stopped and its slot is freed, and the step stays open (`enginehost.stepRun.turnEnded`, `enginehost.stepRun.limitTurn`; `enginehost.Manager.Release`).
- A limited step spends nothing. Its ticks check nothing, so the watch makes no monitor call, and its exits are ignored (`enginehost.stepRun.exited`, `enginehost.stepRun.tick`). The step stays limited through exits and restarts (`enginehost.stepRun.resume`; `enginehost.Steps.Reconcile`). A known reset resumes it through the due pass, 60 seconds past the reset, once for that reset (see [Step lifecycle](contract.md#step-lifecycle), Usage limit; `enginehost.dueGrace`; `store.StepLoop.applyEngine`).
- `step_status` and `step_wait` report the hold in the step object's `limited`, `limitKind` and `limitResets` fields (see [The step object](#the-step-object)). `step_resume` resumes the step (see [step_resume](#step_resume)). `epic_resume` resumes the epic's limited task steps too, and lists them (see [epic_resume](#epic_resume)).
- A planner turn's limited step is stopped at the runner's first timed-out wait that shows it limited (`planner.Runner.await`; see [Planner turns](contract.md#planner-turns)).
- An agent gate step that is limited at a restart stays limited when the restart rebuilds its gate, as it rebuilds an evidence judge's (see [Evidence](contract.md#evidence)); any other agent gate step ends `engine_restarted` (`enginehost.Steps.readoptRun`, `enginehost.stepRowRunsAgentGate`, `enginehost.Steps.readoptAgentGate`, `enginehost.Steps.Reconcile`).
- The owner gets one limit notice for each limit key, `<kind>@<reset>`. It is updated when the steps it names change, and cleared when no step holds that key (`enginehost.LimitNotices`). Its push carries the `limit` key, and so does its clear (`push.clearPayload`, `push.boundedPayload`).

### Caller facts

These are Claude Code 2.1.321 behaviors that the tool shapes answer to. No code or fixture in this repository records them.

- A stdio tool call that stays silent is aborted after 30 minutes (`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`). The 25-minute clamp on `step_wait` keeps a wait inside that limit.
- In an interactive session, a call still running after 120 seconds is moved to the background, unless `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0` is set. Step callers set it to 0.
- A cancelled `step_wait` ends at once and frees its call slot, so the slot is not held until the wait's timeout (see Protocol above).

## 15. The step watch and judge

The findings of this section come from live probes on Claude Code 2.1.321 with `claude-haiku-5-5`, and from the code that runs them. The probe output is not committed, so each claim cites the code that relies on it. The watch and the judge run beside a step's loop, and [Step lifecycle](contract.md#step-lifecycle) gives the rules they follow.

- **Clocks.** The watch never reads the clock. Its loop passes each reading in (`enginehost.stepWatch`, `enginehost.stepRun.Event`). Model time and silence advance only while a turn runs with no main-conversation tool call open. Turn time advances for the whole turn (`enginehost.stepWatch.advance`). A turn start restarts turn time and clears the open calls, and a turn end or an exit clears them too. Any event restarts the silence count (`enginehost.stepWatch.event`).
- **Trips.** The loop checks the watch on each tick, which is five seconds by default (`enginehost.stepDefaultWatchTick`, `enginehost.NewSteps`). A tick raises the first of four trips that is due, in this order (`enginehost.stepWatch.due`). No trip is raised while no turn runs or while a trip waits for its verdict (`enginehost.stepWatch.due`). A landed nudge turns off the periodic check until the next turn begins (`enginehost.stepWatch.due`).
  - `overtime`: model time reaches the step's limit. The limit is `model_limit_seconds` on `StartStep`, 60 minutes when it is zero (`enginehost.stepDefaultModelLimit`, `enginehost.Steps.Start`, `enginehost.stepService.StartStep`).
  - `tool_stuck`: a main-conversation tool call has been open for 30 minutes of wall time, or 60 minutes after its extension (`enginehost.watchToolStuck`, `enginehost.watchToolExtended`, `enginehost.stepWatch.stuckCall`).
  - `silent`: 10 minutes of model time with no event (`enginehost.watchSilence`, `enginehost.stepWatch.due`).
  - `periodic`: five minutes of turn time since the turn began or since the last verdict was applied (`enginehost.watchPeriod`, `enginehost.stepWatch.due`, `enginehost.stepWatch.apply`).
- **Gate limit.** An agent gate step's unheld tick checks its gate's `limit` before the trips, whether or not a turn runs. At the first tick at or past the limit of wall time from the run's start, or from its latest resume from a usage limit (`enginehost.stepRun.resumeWith`), the step ends `overtime` with the reason `agent gate ran past its limit of N seconds`, where N is the limit in seconds. No monitor call is made and no verdict is stored (`enginehost.stepRun.watchGateLimit`, `enginehost.newStepRun`, `enginehost.stepRun.tick`).
- **Monitor call.** A trip makes one call on the step's Haiku caller, and the loop waits for it. It handles no return or exit until the call ends (`enginehost.stepRun.watchTick`, `enginehost.stepRun.run`). The input is the monitor instruction, a `## Why` section with the trip's sentence, and a `## Recent events` section (`enginehost.stepMonitorInput`). The recent events are the last 40 finished blocks and notices, oldest first, each with its age and its text cut to 300 bytes (`enginehost.watchRecentLen`, `enginehost.watchCutBytes`, `enginehost.stepWatch.remember`, `enginehost.watchCut`, `enginehost.stepWatch.restore`, `enginehost.stepWatch.dropNudge`).
- **Argv and environment.** The call runs `claude -p --model claude-haiku-5-5 --settings {"disableAllHooks":true} --no-session-persistence --tools "" --max-turns 1 --output-format json --json-schema <schema>` in `/`. The model is `protocol.DefaultSummaryModel` (`enginehost.haikuArgv`, `enginehost.Haiku.run`, `protocol.DefaultSummaryModel`). Its environment is orreryd's, without `ANTHROPIC_BASE_URL` and `ORRERY_SUMMARIZER`, with `ORRERY_SUMMARIZER=1` added (`enginehost.haikuEnv`).
- **Cap and timeout.** orreryd builds one Haiku caller with the defaults for the whole process (`cmd/orreryd.shutdownServe`, `enginehost.haikuDefaultCap`, `enginehost.haikuDefaultTimeout`). Two calls run at once, shared by every step's monitor and judge calls. Each call has 60 seconds, which covers the wait for a slot and the run together (`enginehost.Haiku.Call`, `enginehost.Haiku.CallVia`). At the timeout the claude process group is killed, and the call waits at most 2 seconds for its output pipes to close (`enginehost.haikuKillGrace`, `enginehost.Haiku.run`, `enginehost.Haiku.call`).
- **Reply.** The call reads the one JSON result line claude prints. It succeeds only for a `result` of subtype `success` that is not `is_error` and carries `structured_output` (`enginehost.haikuResultOutput`).
- **Measured time.** Probes of this argv measured 3.2, 4.0 and 4.0 seconds of wall time per call, with `duration_ms` from 2371 to 2686. The probes also found that the call ends `success` with `structured_output` set under `--max-turns 1`, and that a result with `num_turns` 2 still succeeds under that flag. The reply is read from `structured_output` (`enginehost.haikuResultOutput`).
- **Monitor verdicts.** The reply must match `stepMonitorSchema`, with a `verdict` and a `doing` string (`enginehost.stepMonitorSchema`). The verdicts are:
  - `progressing`: real progress since the last check.
  - `long_command`: one long command that is still plausibly working, such as tests or a build.
  - `looping`: repeated actions without progress.
  - `wedged`: stuck, with no sign of recovery.

  The instruction defines each one (`enginehost.stepMonitorInstruction`), and the constants are at `enginehost.watchVerdictProgressing`, `enginehost.watchVerdictLongCommand`, `enginehost.watchVerdictLooping`, `enginehost.watchVerdictWedged`. A verdict outside the four, or a blank `doing` after trimming, fails the parse (`enginehost.parseStepMonitor`). The `doing` line is the reply's first line, trimmed and cut to 200 bytes at a rune boundary (`enginehost.parseStepMonitor`). The instruction asks for one line under 100 characters, and the code keeps up to 200 bytes (`enginehost.stepMonitorDoingBytes`, `enginehost.stepMonitorInstruction`).
- **Verdict policy.** `apply` acts on a verdict in this order (`enginehost.stepWatch.apply`):
  1. A trip whose turn is no longer the running turn acts as `none`. So does a `tool_stuck` trip whose call has closed (`enginehost.stepWatch.apply`).
  2. `overtime` ends the step `overtime`, whatever the verdict (`enginehost.stepWatch.apply`).
  3. `looping` or `wedged` nudges the step if it has not been nudged. Otherwise it ends the step with that verdict as its end (`enginehost.stepWatch.apply`).
  4. `tool_stuck` with `long_command` extends the call once. Any other verdict ends the step `tool_stuck` (`enginehost.stepWatch.apply`).
  5. `silent` nudges the step if it has not been nudged. Otherwise it ends the step `silent` (`enginehost.stepWatch.apply`).
  6. `periodic` takes `none` (`enginehost.stepWatch.apply`).

  Every apply restarts the periodic count, including an apply that acts as `none` (`enginehost.stepWatch.apply`).
- **Failed call.** A monitor call that fails, or whose reply does not parse, stores its error with an empty verdict and an empty doing line (`enginehost.stepRun.watchMonitor`). The verdict is then empty, so the trip takes its mechanical action: `overtime` and `tool_stuck` end the step, `silent` nudges on its first trip and ends on the next, and `periodic` takes `none` (`enginehost.watchVerdictProgressing`, `enginehost.watchVerdictLongCommand`, `enginehost.watchVerdictLooping`, `enginehost.watchVerdictWedged`). A run with no Haiku caller does the same, with its own error (`enginehost.stepRun.watchMonitor`).
- **Nudge.** The first nudge interrupts the running turn with `Interrupt` (`enginehost.stepRun.watchNudge`, `enginehost.Manager.Interrupt`). It sets the text the next turn end is continued with: the trip's summary and doing line, then `Continue the step where it stopped, or return now if it is finished.` (`enginehost.stepWatch.nudgeSpent`). The interrupt ends the turn with `error_during_execution` (see [What follows an interrupt](#what-follows-an-interrupt)). That turn end is no round. The loop neither checks nor stores it, though an agent gate step keeps the first `fails` result of its output when that output passes `schema` (`enginehost.stepRun.turnEnded`, `enginehost.stepRun.latchNoRound`), and it sends the nudge text with `Continue` (`enginehost.stepRun.turnEnded`). A turn end that is not an error drops the nudge and is an ordinary round (`enginehost.stepRun.turnEnded`).
- **Nudge spending.** A landed nudge spends the step's one nudge, restarts the silence count, and turns off the periodic check until the next turn begins. Until then each open call's 30 minutes, or 60 after its extension, count from the nudge. The silent, tool_stuck and overtime trips keep running in the interrupted turn (`enginehost.stepWatch.nudge`, `enginehost.stepWatch.stuckCall`, `enginehost.stepWatch.event`, `enginehost.stepWatch.due`). A nudge does not count toward the three send-backs. Only `retry` counts those (`enginehost.stepRun.retry`).
- **Failed interrupt.** A failed `Interrupt` is logged, the action is `none`, and the nudge is undone. The step's nudge is not spent, open calls count from their start again, and the watch keeps watching the running turn (`enginehost.stepRun.watchNudge`, `enginehost.stepWatch.restore`). A failed `Continue` of a nudge ends the step `failed` (`enginehost.stepRun.continueStep`).
- **Extension.** A `long_command` verdict on a `tool_stuck` trip extends that call once, from 30 minutes to 60 minutes of wall time. The extension belongs to that call, so a later call has its own (`enginehost.watchCall`, `enginehost.stepWatch.stuckCall`, `enginehost.stepWatch.apply`).
- **Watch ends.** A watch end stores its verdict first. A failure to store it ends the step `failed` (`enginehost.stepRun.watchTick`). The step then ends with the verdict's end kind, no status, and the reason `<trip> trip: <why>`, followed by ` Doing: <doing>` when the doing line is not empty (`enginehost.stepRun.watchTick`, `enginehost.watchLoopSummary`). The watch ends the step `overtime`, `tool_stuck`, `silent`, `looping` or `wedged` (`enginehost.watchEndSilent`, `enginehost.watchEndToolStuck`, `enginehost.watchEndOvertime`, `enginehost.stepWatch.apply`). The judge ends the step `goal_unmet` (`enginehost.judgeLoopEndGoalUnmet`). The gate limit's `overtime` (see Gate limit) makes no monitor call and stores no verdict row, so the first sentence does not apply to it.
- **Verdicts in the store.** Each verdict is appended to the row's `verdicts` with its time, its kind (`monitor` or `judge`), its trip, its round, its verdict, its detail, its error and its action (`store.StepVerdict`, `store.StepWatch.applyEngine`). A monitor's detail is its doing line (`enginehost.stepRun.watchTick`). A judge's detail is its reason (`enginehost.stepRun.judgeReturn`). A non-empty doing line replaces the row's `doing` (`store.StepWatch.applyEngine`).
- **Judge.** A return that passes every check and whose `status` equals `done_value` is judged, except an agent gate step's return, which is never judged: its verdict ends it `done` or `gate_failed`, as [Checks](contract.md#step-lifecycle) gives (`enginehost.stepRun.judge`, `enginehost.stepRun.endVerdict`). A return that fails a check is sent back and is not judged (`enginehost.stepRun.judge`), except a failed `checkout` check of a read-only step, which ends the step `checks_failed` at once with nothing sent back (`enginehost.stepRun.judge`). Without a Haiku caller the judge makes no call, and the step ends `done` (`enginehost.stepRun.judgeReturn`).
- **Judge input.** The input is the judge instruction, then `## Task` with the step's first prompt, then `## Return` with the return. A writing step adds `## Diff stat`, the `git diff --stat` from the start commit to the return's commit. A step with a gate adds `## Gate stdout tail` and `## Gate stderr tail`, the stdout and stderr tails its gate check kept, each in its own section. The gate's record and exit status are not in the input (`enginehost.stepJudgeInstruction`, `enginehost.stepJudgeInput`, `enginehost.stepRun.judgeCall`, `enginehost.judgeGateTails`). A blank diff stat or gate tail is omitted (`enginehost.stepJudgeInput`). The task and the return are kept whole up to 16 KiB. A longer one keeps its first 8 KiB and its last 8 KiB, with a line `[<n> bytes left out]` between them, where `<n>` counts the bytes left out (`enginehost.stepJudgeEnds`). The diff stat keeps its first 8 KiB, and each gate tail keeps its last 8 KiB (`enginehost.stepJudgeSectionBytes`, `enginehost.stepJudgeHead`, `enginehost.stepJudgeTail`). The instruction tells the judge that a section with a bytes-left-out line lost only its middle, which does not mean the return was cut off (`enginehost.stepJudgeInstruction`).
- **Judge verdicts.** The reply is `met` or `unmet`, with a one-line reason (`enginehost.stepJudgeSchema`, `enginehost.parseStepJudge`).
  - `met` ends the step `done` (`enginehost.stepRun.judgeReturn`).
  - The first `unmet` stores its verdict with action `continue`, sends the session back once with the reason, and waits for the next return. That return is judged again when it passes its checks (`enginehost.stepRun.judgeReturn`, `enginehost.judgeLoopContinueText`). The send-back does not count toward the three send-backs (`enginehost.stepRun.retry`).
  - A second `unmet` ends the step `goal_unmet`, and the step's return is kept (`enginehost.stepRun.judgeReturn`).
  - A failed diff stat, a failed call or an unparsable reply stores its error with no verdict and action `none`, and ends the step `done` (`enginehost.stepRun.judgeReturn`, `enginehost.stepRun.judgeCall`).
  - A failed `Continue` of the judge's send-back ends the step `failed` (`enginehost.stepRun.judgeReturn`).
